# Go 코드 실행과 채점 설계

학습자가 쓴 Go 코드를 로컬 서버가 컴파일·실행·채점하는 방식과, 그 위에 올리는 문제 유형·에디터·콘텐츠 형식을 설계합니다.
결정 요약은 [G-002](/docs/decisions.md#g-002-go-코드-실행과-채점--확정)입니다.

- 상태: 승인됨
- 작성: AI 초안, 사용자 승인(2026-11-25)
- 최종 수정: 2026-11-25
- 관련 문서: [결정 기록](/docs/decisions.md), [JavaScript 코드 실행 샌드박스 설계][js-sandbox], [JavaScript 콘텐츠·문제 시스템 설계][js-content]

[js-sandbox]: https://github.com/ProgInOne/javascript/blob/develop/docs/design/code-execution-sandbox.md
[js-content]: https://github.com/ProgInOne/javascript/blob/develop/docs/design/content-and-exercises.md

## 배경과 범위

Go 저장소의 뼈대(G-001)는 레슨과 선택형 문제만 다루고 Go 코드를 실행하지 않습니다.
학습자가 코드를 직접 쓰고 실행하고 채점받으려면 다음 네 가지가 필요합니다.

1. Go 도구 체인을 어디서 얻는가
1. 신뢰할 수 없는 코드를 어디서 어떻게 격리해 실행하는가
1. 실행 결과를 누가 어떻게 판정하는가
1. 에디터, 문제 유형, 레슨의 실행 예제를 어떻게 만드는가

학습자 코드와 AI가 만든 콘텐츠(문제의 테스트 코드, 예제 코드)는 모두 신뢰할 수 없는 입력으로 다룹니다.
JavaScript 앱은 브라우저 샌드박스에서 실행하고 서버가 관측값을 비교합니다([JS D-018][js-decisions]).
Go는 브라우저가 직접 실행할 수 없으므로 실행 위치부터 다시 정합니다.

[js-decisions]: https://github.com/ProgInOne/javascript/blob/develop/docs/decisions.md

## 목표와 비목표

### 실행 목표

- 학습자 코드가 학습자 컴퓨터의 파일, 네트워크, 다른 프로세스에 접근할 수 **없어야 한다**.
  콘텐츠의 테스트 코드도 같은 격리 안에서만 실행합니다.
- 코드를 고친 뒤 실행 결과가 1초 안에 보여야 한다(빌드 캐시가 있을 때).
- 컴파일 오류와 런타임 오류는 실제 Go 도구가 낸 문구를 그대로 보여 준다.
  레슨이 가르치는 메시지와 학습자가 나중에 터미널에서 볼 메시지가 같아야 하기 때문입니다([JS D-030][js-decisions]과 같은 원칙).
- 정답 키(기대 출력, 테스트 사례)는 서버를 떠나지 않는다.
- 같은 코드는 같은 결과를 낸다. 채점과 콘텐츠 검증이 흔들리지 않게 합니다.

### 실행 비목표

- **표준 라이브러리 밖의 모듈.** 외부 모듈을 받으면 네트워크가 필요하고 공급망 위험이 생깁니다. 입문 과정은 표준 라이브러리로 충분합니다.
- **파일 입출력, 네트워크, 프로세스 실행을 다루는 실습.** 격리 목표와 충돌합니다. 이런 주제는 레슨 본문과 선택형 문제로 다룹니다.
- **실제 병렬 실행.** 실행 환경은 스레드 하나입니다. 고루틴과 채널은 동작하지만 `runtime.NumCPU()`는 1이고 데이터 경쟁이 실제로 드러나지 않습니다. 경쟁 상태는 개념 설명과 예측 문제로 다룹니다.
- **Go 도구 체인을 앱에 내장하기.** 처음에는 학습자가 설치한 Go를 씁니다. 공식 배포판을 앱이 받아 주는 기능은 필요할 때 더합니다.

## 설계

### 실행 흐름 개요

```text
웹(에디터) ──코드──▶ 서버 ──▶ ① 임시 모듈 작성
                              ② go build (GOOS=wasip1, GOARCH=wasm, 깨끗한 환경)
                              ③ Worker 스레드에서 wasm 실행 (최소 WASI, 한도)
                              ④ 출력·오류·종료 코드 수집
                              ⑤ 채점이면 체크 판정
웹 ◀──결과(출력, 오류, 체크 결과)── 서버
```

- 컴파일과 실행은 모두 로컬 서버(`apps/server`)가 합니다. 실행기는 `packages/go-runner`에 두고, 서버와 콘텐츠 도구(`content:check --run`)가 함께 씁니다.
- 웹은 코드와 표준 입력만 보내고, 결과를 받아 보여 줍니다. 서버는 실행 결과가 붙은 채점 요청(`runResult`)을 계속 거부합니다.

### Go 도구 체인 찾기와 버전

- 서버는 시작할 때와 설정을 바꿀 때 `go`를 찾습니다.
  순서는 설정의 경로, `PATH`, 각 OS의 표준 설치 위치(macOS `/usr/local/go/bin`, `/opt/homebrew/bin`, Windows `C:\Program Files\Go\bin`, Linux `/usr/local/go/bin`)입니다.
- `go version`과 `go env GOROOT`로 버전과 위치를 확인하고, `gofmt`는 `GOROOT/bin`에서 찾습니다.
- **최소 버전은 Go 1.22**입니다.
  `wasip1` 대상은 1.21부터 있고, 1.22에서 `for` 반복 변수가 반복마다 새로 만들어지도록 바뀌어 같은 코드의 출력이 달라질 수 있기 때문입니다.
- 콘텐츠의 기대 출력은 CI의 고정 버전(저장소 루트의 `.go-version`)으로 검증합니다. 학습자 버전의 마이너 버전이 이와 다르면 설정 화면과 실행 결과에 "출력이나 오류 문구가 다를 수 있어요"를 알립니다.
- Go가 없거나 1.22보다 낮으면 실행 기능을 끄고 설치 방법(go.dev/dl 링크)을 안내합니다. 선택형 문제와 레슨 읽기는 그대로 됩니다.

### 컴파일

컴파일도 신뢰할 수 없는 입력을 다루는 단계로 보고 다음을 지킵니다.

- **임시 모듈.** 실행마다 앱 데이터 폴더의 임시 디렉터리에 `go.mod`(서버가 씀, `go 1.22`)와 학습자 파일, 필요하면 서버가 만든 하네스 파일만 둡니다. 학습자 파일 이름은 서버가 정합니다(`main.go` 등). 끝나면 지웁니다.
  `go.mod`의 `go` 줄이 언어 버전을 정하므로, 학습자의 Go가 더 새 버전이어도 반복 변수 같은 언어 의미는 1.22 기준으로 같습니다.
- **깨끗한 환경.** 부모 프로세스의 환경 변수를 물려주지 않고 다음만 넘깁니다.
  - `GOOS=wasip1`, `GOARCH=wasm`, `CGO_ENABLED=0`
  - `GOTOOLCHAIN=local`: `go.mod`나 환경 때문에 다른 도구 체인을 내려받지 않게 합니다.
  - `GOPROXY=off`, `GOSUMDB=off`, `GOFLAGS=-mod=mod`: 모듈을 내려받지 않습니다. 표준 라이브러리 밖의 import는 컴파일 오류가 됩니다.
  - `GOENV=off`: 사용자의 `go env -w` 설정(예: `GOFLAGS=-toolexec=…`)이 끼어들지 못하게 합니다.
  - `GOCACHE=<데이터 폴더>/cache/go-build`, `GOPATH`·`GOMODCACHE`는 데이터 폴더 아래 빈 디렉터리, `HOME`·`TMPDIR`도 데이터 폴더 아래로 둡니다.
- **할 수 없는 일.** cgo는 꺼져 있고 `wasip1`은 cgo를 지원하지 않습니다. `go build`는 `//go:generate`를 실행하지 않습니다. `//go:embed`는 모듈 디렉터리 밖을 가리킬 수 없고, 임시 모듈에는 학습자 파일만 있습니다.
- **한도.** 컴파일은 30초(첫 빌드는 표준 라이브러리를 `wasip1`용으로 처음 컴파일해 몇 초 걸림), 출력 64KB. 넘으면 프로세스를 끝냅니다.
- **미리 데우기.** 서버가 시작하면 빈 프로그램을 한 번 컴파일해 빌드 캐시를 채웁니다. 시험 측정(go1.27.3, Apple Silicon)에서 첫 빌드는 약 2초, 코드를 고친 뒤 다시 빌드는 약 0.3초였습니다.
- 컴파일 오류는 `./main.go:5:4: …` 형식을 그대로 쓰고, 파일 이름·줄·열을 따로 뽑아 에디터에 표시합니다. 하네스 파일의 오류는 학습자에게 내부 오류로 보이고 로그에 남깁니다.

### 실행: 최소 WASI와 Worker 스레드

- 컴파일한 `.wasm`은 서버 프로세스 안의 Worker 스레드(`node:worker_threads`)에서 실행합니다. 실행마다 새 Worker를 만듭니다.
- **WASI 가져오기(import)는 직접 구현합니다.** Node의 `node:wasi`는 실험 단계이고, 공식 문서도 파일 시스템 격리를 보장하지 않는다고 밝힙니다. Go `wasip1` 프로그램이 가져오는 함수는 19개뿐이라 직접 만들어 무엇을 여는지 코드로 통제합니다.

| WASI 함수 | 동작 |
|---|---|
| `fd_write` | 1(표준 출력), 2(표준 오류)만 받아 버퍼에 모음. 다른 번호는 `EBADF` |
| `fd_read` | 0(표준 입력)만, 요청에 담긴 입력에서 읽음 |
| `clock_time_get` | 가상 시계(아래) |
| `poll_oneoff` | 시계 구독만 처리해 가상 시계를 앞으로 보냄. 파일 구독은 `ENOTSUP` |
| `random_get` | 실행마다 정한 시드의 결정론적 난수(채점·검증) 또는 진짜 난수(자유 실행) |
| `args_*`, `environ_*` | 프로그램 이름 하나, 환경 변수 없음 |
| `proc_exit` | 종료 코드를 기록하고 실행을 끝냄 |
| `sched_yield` | 아무것도 하지 않음 |
| `fd_close`, `fd_fdstat_*`, `fd_filestat_get` | 0·1·2번에만 최소 정보, 나머지 `EBADF` |
| `fd_prestat_*`, `path_open`, `path_filestat_get` | 열어 준 디렉터리가 없으므로 `EBADF`/`ENOENT` |

- **가상 시계.** `time.Now()`는 고정된 시각(2009-11-10 23:00:00 UTC, Go Playground와 같은 시각)에서 시작하고, `time.Sleep`은 실제로 기다리지 않고 가상 시계만 앞으로 보냅니다.
  채점과 콘텐츠 검증이 빠르고 매번 같은 결과가 됩니다.
  대신 경과 시간을 재는 코드는 잠든 시간만큼만 나옵니다. 레슨의 실행 예제에서 이 차이를 안내합니다.
- **한도.**
  - 실행 시간: 벽시계 기준 5초. 넘으면 `Worker.terminate()`로 끝냅니다(Wasm 안의 무한 반복도 멈춤).
  - 메모리: Wasm 메모리 최대 크기를 256MB로 제한합니다. 모듈을 인스턴스화하기 전에 메모리 섹션의 최대값을 고쳐 넣어, 넘으면 Go 런타임이 메모리 부족으로 끝나게 합니다.
  - 출력: 표준 출력과 표준 오류를 합쳐 64KB. 넘으면 잘라 내고 실행을 끝냅니다.
  - 동시 실행: 서버 전체에서 두 개. 나머지는 차례를 기다립니다.
- 결과는 표준 출력, 표준 오류, 종료 코드, 끝난 이유(`exit`, `panic`, `timeout`, `memory`, `output-limit`), 걸린 시간입니다. `panic`은 표준 오류의 `panic:`/`goroutine` 블록과 종료 코드 2로 판별합니다.

### 채점

- 서버가 실행하고 서버가 판정합니다. 웹이 받는 것은 체크별 통과 여부와 학습자에게 보여 줄 설명뿐입니다.
- 처음 만드는 체크 종류:
  - `stdout`: 출력 전체 일치, 포함, 줄 단위 비교. 끝 줄바꿈과 줄 끝 공백의 처리를 스펙에서 정합니다.
  - `compile`: 컴파일되어야 함, 또는 특정 오류(파일 기준 줄과 문구 일부)가 나야 함.
  - `call`: 함수 호출 결과(아래).
  - `exit`: 종료 코드나 `panic` 여부.
- **`call` 체크는 YAML 사례 표에서 하네스를 생성합니다.**
  사례마다 인수와 기대값을 Go 식 문자열로 적으면(`args: ['3', '"go"']`, `want: '6'`), 서버가 학습자 함수를 부르는 `main`을 생성하고, 결과를 `reflect.DeepEqual`로 비교해 사례별 결과를 JSON 한 줄로 표준 출력에 씁니다.
  하네스는 학습자 코드와 같은 `main` 패키지의 다른 파일입니다. 그래서 `entry`가 있는 문제는 학습자 코드에 `main` 함수를 두지 않고, 학습자가 `main`을 쓰면 컴파일 오류 대신 "이 문제는 함수만 작성해요" 안내로 알립니다.
  학습자 코드가 하네스의 JSON 줄을 흉내 낼 수 없게, 하네스 출력 줄에는 실행마다 바뀌는 비밀 표지(서버가 만든 난수)를 붙입니다.
- 소스 구조 검사(예: "`for` 문을 써야 해요")는 처음 범위에 넣지 않습니다. 필요해지면 `go/ast`로 분석하는 도구를 같은 샌드박스에서 실행하는 방식으로 설계합니다.

### 문제 유형과 만드는 순서

| 순서 | 유형 | 채점 |
|---|---|---|
| 1 | `predict_output` 출력 예측 | 빌드 때 실제 실행으로 계산한 출력과 비교 |
| 1 | `implement_function` 코드 작성 | `entry`가 있으면 `call`, 없으면 프로그램 전체의 `stdout`([JS D-028][js-decisions]과 같음) |
| 2 | `fix_bug` 버그 고치기, `fill_blank` 빈칸 채우기 | 고친 코드를 실행해 체크 |
| 3 | `parsons` 줄 순서 맞추기, `find_bug_line` 버그 줄 찾기 | 정답 순서·줄과 비교(실행은 검증 때만) |

- 유형 정의는 이 저장소의 `packages/exercise-kit`에 더합니다. JavaScript와 어디까지 공통인지는 3차 분리에서 정합니다.
- 파라메트릭 템플릿([JS D-058][js-decisions])은 위 유형이 자리 잡은 뒤 같은 원칙(빌드 때 실행 검증한 시드 풀)으로 만듭니다.

### 에디터

- core의 주입형 `CodeEditor`(CodeMirror 6, [JS D-008][js-decisions])에 `@codemirror/lang-go`를 붙입니다. 들여쓰기는 탭(폭 4)입니다.
- **"gofmt로 정리"** 버튼이 서버의 `gofmt`를 실행합니다. 입력은 표준 입력으로 넘기고 2초 제한을 둡니다. 문법 오류가 있으면 코드를 바꾸지 않고 오류를 보여 줍니다.
- 컴파일 오류는 해당 줄·열에 진단으로 표시합니다.
- 그동안 숨겨 둔 "작업대 테마" 설정(G-001 뒤 정리)을 다시 보여 줍니다.

### 콘텐츠 형식

- 레슨의 `RunnableExample`(실행 예제)과 `TryIt`(직접 써 보기), `usage: try` 문제를 Go용으로 되살립니다. 이름과 속성은 JavaScript와 같게 둡니다.
- `pnpm content:check --run`이 레슨의 실행 예제와 모든 코드 문제를 실제 Go로 실행합니다.
  예측 문제의 기대 출력은 저자가 쓰지 않고 이 실행 결과로 계산해 `content/.generated/`에 기록합니다(JavaScript의 예측 문제 기대값 파일과 같은 방식).
  모범 답안이 모든 체크를 통과하는지, 시작 코드가 통과하지 않는지도 확인합니다.
- CI는 GitHub 소유 액션 `actions/setup-go`로 `.go-version`의 Go를 설치하고 `content:check --run --frozen`을 실행합니다. 기록과 실행 결과가 다르면 실패합니다.
- 이 단계가 끝나면 `usage: try`와 프로젝트 단원(`kind: project`)을 엽니다. 프로젝트 단원의 형식은 그때 따로 정합니다.

### 진행 순서

1. G-002와 이 설계 문서
1. `packages/go-runner`: 컴파일, 최소 WASI, 한도, 테스트
1. 서버: 실행 API, `gofmt`, Go 도구 찾기와 버전 안내
1. 웹: 에디터, 실행 결과 화면, `RunnableExample`·`TryIt`
1. `content:check --run`과 CI의 Go 설치
1. 문제 유형을 위 순서대로 하나씩

## 검토한 대안

### 도구 체인을 앱이 내려받기

- 장점: 학습자가 Go를 설치하지 않아도 됩니다. 버전을 고정해 콘텐츠와 출력이 항상 같습니다.
- 단점: 플랫폼별 배포판(약 70MB) 다운로드, 체크섬 검증, 업데이트를 앱이 맡아야 합니다. Go를 배우는 학습자는 어차피 Go를 설치합니다.
- 결정: 처음에는 학습자의 Go를 쓰고, 설치가 학습의 걸림돌이 되면 선택 기능으로 더합니다.

### Go Playground로 원격 실행

- 장점: 로컬 설치가 필요 없습니다.
- 단점: 외부 프로그램이 쓰도록 공식 지원하는 API가 아니고, 학습자 코드를 외부 서비스로 보냅니다. 오프라인에서 동작하지 않습니다.
- 결정: 쓰지 않습니다.

### 브라우저의 JavaScript 샌드박스 셸에서 Wasm 실행

- 장점: 앱 CSP와 iframe 격리가 한 겹 더 생깁니다. JavaScript 러너 셸을 다시 쓸 수 있습니다.
- 단점: 채점이 다시 "브라우저가 관측하고 서버가 비교하는" 방식이 되어 `call` 하네스의 결과를 클라이언트가 보고하게 됩니다. 콘텐츠 검증(`content:check --run`)에 브라우저가 필요해집니다. 2.6MB 안팎의 Wasm을 매번 서버에서 브라우저로 보냅니다.
- 결정: 쓰지 않습니다. 최소 WASI는 열어 준 기능만 쓸 수 있는 능력 기반 격리라, 서버 안에서도 파일·네트워크·프로세스에 닿지 않습니다.

### 일반 실행 파일로 직접 실행

- 장점: 가장 빠르고, 진짜 병렬 실행과 파일·네트워크 실습이 됩니다.
- 단점: 학습자 코드와 콘텐츠의 테스트 코드가 사용자 권한으로 모든 파일과 네트워크에 접근합니다. OS별 격리 수단이 제각각이고, macOS의 `sandbox-exec`는 지원 중단된 기능입니다.
- 결정: 쓰지 않습니다.

### Docker 컨테이너

- 장점: 격리가 강하고 실제 Linux 환경입니다.
- 단점: 학습자가 Docker를 설치하고 켜 두어야 하고, 실행마다 컨테이너를 띄우는 비용이 큽니다.
- 결정: 쓰지 않습니다.

### Go 인터프리터(yaegi 등)

- 장점: 컴파일 없이 바로 실행합니다.
- 단점: 오류 문구와 일부 의미가 실제 Go 컴파일러와 다릅니다. 실행 목표의 "실제 문구 그대로"를 지킬 수 없습니다.
- 결정: 쓰지 않습니다.

### `node:wasi` 모듈

- 장점: 직접 구현할 것이 없습니다. 시험 실행에서 Go `wasip1` 프로그램이 그대로 동작했습니다.
- 단점: 실험 단계(Stability 1)이고, 공식 문서가 보안 격리를 보장하지 않는다고 밝힙니다. 가상 시계, 결정론적 난수 같은 채점용 동작을 넣을 수 없습니다.
- 결정: 쓰지 않고, 같은 인터페이스를 최소한으로 직접 구현합니다.

### `call` 체크를 Go 테스트 파일(`_test.go`)로 쓰기

- 장점: 저자가 Go 테스트를 그대로 쓸 수 있어 표현이 자유롭습니다.
- 단점: 사례별 결과와 학습자용 설명을 구조화하기 어렵고, 콘텐츠가 임의의 Go 코드를 더 많이 담게 됩니다.
- 결정: 처음에는 YAML 사례 표로 하네스를 생성합니다. 프로젝트 단원에서 필요하면 테스트 파일 방식을 더합니다.

## 교차 관심사

### 보안

- 신뢰 경계는 두 개입니다. 컴파일(깨끗한 환경, 임시 모듈, 시간 제한)과 실행(최소 WASI, Worker, 한도)입니다.
- Wasm 모듈은 우리가 넘긴 함수 외에는 바깥과 통할 수 없습니다. 열어 준 디렉터리가 없고 소켓 함수가 없으므로 파일과 네트워크에 닿지 않습니다.
- 실행 API는 지금처럼 `127.0.0.1`·`localhost` 호스트와 앱 출처만 받습니다.
- 남은 위험:
  - Go 컴파일러나 V8의 Wasm 구현에 있는 취약점. 도구 체인은 학습자가 관리하므로 최소 버전 안내로 대응합니다.
  - 컴파일러를 오래 붙잡는 입력(거대한 상수 식 등). 시간 제한으로 끊습니다.

### 성능

- 다시 빌드 약 0.3초, Wasm 컴파일·인스턴스화는 수십 ms 수준입니다(구현 때 측정해 테스트 가이드에 적음).
- 빌드 캐시는 데이터 폴더에 둡니다. 백업 대상에서는 뺍니다.

### 관측성

- 실행마다 단계별 시간(컴파일, 실행), 끝난 이유, 한도 초과를 서버 로그에 남깁니다. 학습자 코드와 출력은 로그에 남기지 않습니다.

### 접근성

- 실행 결과와 컴파일 오류는 화면 낭독기가 읽을 수 있는 텍스트로 보여 줍니다. 에디터의 진단은 키보드로 이동할 수 있어야 합니다.

### 테스트

- `go-runner`는 실제 Go로 컴파일·실행하는 테스트를 둡니다(파일 접근 실패, 무한 반복 시간 초과, 메모리 한도, 출력 한도, 가상 시계, 컴파일 환경 격리).
- CI의 두 검사 모두 `actions/setup-go`로 Go를 설치합니다.

## 미결 사항

- Windows에서의 도구 체인 경로와 임시 디렉터리 정리 동작은 구현 때 확인합니다.
- 표준 입력을 쓰는 문제의 입력 형식(문제 스펙의 `stdin`)은 첫 코드 문제 유형을 만들 때 정합니다.
- 숙련도 계산의 유형별 가중치는 코드 문제가 생긴 뒤 다시 봅니다.
